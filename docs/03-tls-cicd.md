# 03. TLS와 CI/CD — 조용히 실패하는 것들

이 문서는 **에러를 내지 않고 실패하는** 종류의 문제를 다룹니다. 로그에 아무것도 남지
않은 채 며칠 뒤 또는 90일 뒤에 서비스가 죽는 구성들입니다.

---

## 1. 인증서 갱신이 리다이렉트에 삼켜지는 문제

HTTP로 들어온 요청을 전부 HTTPS로 넘기는 것은 표준적인 구성입니다.

```nginx
server {
    listen 80;
    location / {
        return 301 https://$host$request_uri;
    }
}
```

Let's Encrypt의 HTTP-01 검증은 `http://<도메인>/.well-known/acme-challenge/<토큰>`에
파일을 두고 인증 기관이 그것을 읽어가는 방식입니다. 위 설정은 **이 요청까지 301로
넘깁니다.** 검증이 실패하고, 갱신이 실패하고, 서비스는 90일 동안 멀쩡히 동작하다가
인증서 만료일에 죽습니다.

해결은 `^~` 수정자로 챌린지 경로를 리다이렉트보다 우선시키는 것입니다.

```nginx
server {
    listen 80 default_server;
    server_name _;

    # ^~ 로 아래 리다이렉트보다 우선한다. 이게 없으면 갱신이 301 로 튕긴다.
    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://api.example.com$request_uri;
    }
}
```

### 리다이렉트 대상에 `$host`를 쓰지 않은 이유

`$host`는 클라이언트가 보낸 Host 헤더를 그대로 씁니다. 원시 IP나 이전에 쓰던 임시
도메인으로 요청이 들어오면 **인증서에 없는 이름으로 HTTPS 리다이렉트가 발생해** TLS
핸드셰이크가 깨집니다. 인증서에 담긴 이름으로 고정하는 편이 안전합니다. 도메인을 바꿀
때 `ssl_certificate` 두 줄과 함께 고쳐야 하는 지점이라는 것만 주석으로 남겨두면 됩니다.

### 갱신 스케줄

```cron
0 3 * * 1 cd /srv/app && docker compose -f deploy/docker-compose.yml \
  run --rm certbot renew --quiet && \
  docker compose -f deploy/docker-compose.yml exec -T web nginx -s reload
```

`certbot renew`는 만료 30일 전부터만 실제로 갱신하므로 매일 돌릴 필요가 없습니다.
**주 1회면 30일 창 안에 네 번의 기회**가 생겨 한두 번 놓쳐도 됩니다. 갱신 후 nginx를
reload해야 새 인증서를 읽으며, reload는 무중단입니다.

certbot 컨테이너는 Compose profile로 묶어 평소에는 기동하지 않고 발급·갱신 시에만
`run --rm`으로 띄웁니다. 상시 떠 있을 이유가 없는 프로세스입니다.

> **주의** 인스턴스를 장기간 중지해 두면 그 사이 cron이 아예 돌지 않습니다. 개발 비용을
> 아끼려고 인스턴스를 껐다 켜는 운영을 한다면, 재기동 후 인증서 상태를 확인해야 합니다.

## 2. 도메인 교체 — 순서가 곧 롤백 가능성

임시 도메인에서 정식 도메인으로 옮길 때, 순서를 잘못 잡으면 중간에 서비스가 끊깁니다.
되돌릴 수 있는 구간과 없는 구간을 나눠 설계했습니다.

새 도메인의 A 레코드를 인스턴스 IP로 연결한 뒤:

1. **두 이름을 모두 담은 인증서 발급** (병행 기간용)
   ```bash
   certbot certonly --webroot -w /var/www/certbot \
     --cert-name api.example.com \
     -d api.example.com -d old.example.com
   ```
   `--cert-name`을 지정하지 않으면 certbot이 `<이름>-0001` 형태의 새 계보를 만들어
   nginx가 참조하는 경로와 어긋납니다.

2. `ssl_certificate` 두 줄을 새 계보로 교체 → nginx 재시작

3. CORS 허용 목록에 **두 도메인을 모두** 추가 → API 재기동

4. 프론트엔드 재빌드 및 배포 — API 주소가 빌드 타임에 번들에 박히므로 재빌드가 필요합니다

5. HTTP 리다이렉트 대상을 새 도메인으로 고정

**4번까지가 되돌릴 수 있는 구간입니다.** 이 시점까지는 두 도메인이 모두 동작하므로
문제가 생기면 프론트엔드만 이전 번들로 되돌리면 됩니다. 5번을 실행하는 순간 구 도메인
경로가 닫힙니다.

브라우저 개발자 도구의 Network 탭에서 **`http://` 요청이 하나도 없는지** 확인하는 것이
마지막 관문입니다. 하나라도 있으면 mixed content로 차단되는데, 이 차단은 서버 로그에
남지 않습니다.

## 3. CI/CD 파이프라인

### CI — 모든 푸시와 PR에서

```
checkout → 의존성 설치 → ruff (lint) → pytest + coverage → 리포트 업로드
```

외부 의존성(DB·Redis)이 필요한 테스트는 마커로 분리해 CI 환경에서 자동으로 건너뜁니다.
CI가 통과했는지 여부가 신뢰를 잃는 가장 빠른 길은 **환경 탓으로 실패하는 테스트를
방치하는 것**입니다.

### CD — main 브랜치 푸시에서

```
checkout
  → AWS 자격증명 구성
  → ECR 로그인
  → 이미지 빌드 & 푸시 (태그 = 커밋 SHA)
  → 현재 태스크 정의 조회
  → 새 이미지로 태스크 정의 갱신
  → ECS 서비스 배포 (서비스 안정화까지 대기)
```

**이미지 태그를 `latest`가 아니라 커밋 SHA로 잡았습니다.** `latest`는 어떤 커밋이 지금
돌고 있는지 알 수 없게 만들고, 롤백할 대상을 특정할 수 없게 합니다. SHA 태그면 이전
태스크 정의 리비전으로 되돌리는 것만으로 롤백이 끝납니다.

**`wait-for-service-stability`를 켰습니다.** 이것이 없으면 배포 잡은 성공으로 끝나고
새 태스크는 헬스체크에 실패해 롤백되는 상황이 벌어집니다. CI가 초록불인데 서비스는
이전 버전인 상태가 가장 위험합니다.

**빌드 컨텍스트를 리포지토리 루트로 잡았습니다.** 백엔드 디렉터리를 컨텍스트로 두면
그 형제 디렉터리에 있는 공유 모듈이 이미지에 들어가지 않아, 로컬에서는 되고 컨테이너
안에서만 import 에러가 나는 상황이 생깁니다.

## 4. 자격증명 관리

### 현재 구성과 한계

CI/CD는 GitHub Secrets에 저장한 액세스 키로 AWS에 인증합니다. 동작하지만 **장기
자격증명이라는 점이 구조적 약점**입니다. 유출되면 수동으로 회수하기 전까지 유효하고,
회전은 사람이 기억해야 합니다.

개선 방향은 **GitHub OIDC 페더레이션**입니다. GitHub Actions가 발급받은 단기 토큰을
AWS가 신뢰하도록 IAM 역할에 신뢰 정책을 걸면, 저장되는 장기 키가 사라집니다. 특정
리포지토리·특정 브랜치에서 온 워크플로만 역할을 맡을 수 있도록 조건을 걸 수 있습니다.

### 애플리케이션 자격증명

실행 중인 컨테이너가 S3에 접근할 때는 액세스 키를 환경변수로 넣지 않고 **태스크 IAM
역할**을 쓰는 것이 원칙입니다. SDK가 메타데이터 엔드포인트에서 임시 자격증명을 자동으로
받아가므로 코드와 설정 어디에도 키가 남지 않고, 만료·회전이 자동입니다.

### 원칙

- 자격증명은 코드·이미지·리포지토리 어디에도 들어가지 않습니다
- 프로덕션 환경변수는 CI 단계에서 시크릿으로 주입하고, 관리형 구성에서는 Secrets Manager를 씁니다
- GCP 서비스 계정 키처럼 파일이어야 하는 자격증명은 **읽기 전용 마운트**로 넣고, 그것을 필요로 하는 컨테이너에만 붙입니다 — 워커가 LLM을 호출하지 않는다면 워커에는 키가 없어야 합니다
