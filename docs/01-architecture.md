# 01. 아키텍처 — 단일 박스에서 관리형 구성으로

## 출발점

서비스 초기에는 검증 속도가 전부였습니다. 프론트엔드와 백엔드를 붙여보고, 실제 HTTPS
환경에서 동작을 확인하는 것이 우선이었기 때문에 **EC2 한 대에 전부 올리는 구성**으로
시작했습니다.

```
                      Internet
                         │
                    ┌────▼─────┐
                    │ Elastic  │
                    │    IP    │
                    └────┬─────┘
                         │  :80 / :443
              ┌──────────▼───────────┐
              │        nginx         │  TLS 종단 · SPA 서빙
              │  (단일 외부 입구)      │  /api → 리버스 프록시
              └──────────┬───────────┘
                         │
      ┌──────────────────┼──────────────────┐
      │                  │                  │
┌─────▼─────┐     ┌──────▼──────┐    ┌──────▼──────┐
│    api    │     │   worker    │    │    beat     │
│ (FastAPI) │     │  (Celery)   │    │ (스케줄러)   │
└─────┬─────┘     └──────┬──────┘    └──────┬──────┘
      │                  │                  │
      └──────────┬───────┴──────────────────┘
                 │
        ┌────────┴────────┐
        │                 │
┌───────▼──────┐   ┌──────▼──────┐
│  PostgreSQL  │   │    Redis    │
│  (pgvector)  │   │             │
└──────────────┘   └─────────────┘

모두 같은 EC2 인스턴스 위의 컨테이너
```

### 이 구성에서 의도적으로 정한 것들

**외부 입구를 하나로 고정했다.** API 컨테이너의 포트를 `127.0.0.1:8000`에만 바인딩해
루프백 밖으로 나가지 못하게 했습니다. 디버깅할 때는 SSH 터널로 접근할 수 있으면서,
외부에서 nginx를 우회해 API에 직접 닿는 경로는 존재하지 않습니다. 보안 그룹만으로 막는
것과 달리 인스턴스 안에서도 노출면이 없습니다.

**업로드 파일은 named volume 하나를 공유한다.** api가 파일을 쓰고, worker가 읽어서
인식 작업을 하고, nginx가 정적으로 서빙합니다. 세 컨테이너가 같은 볼륨을 물되 worker와
nginx는 읽기 전용입니다. 호스트 디렉터리를 각자 두면 api가 저장한 경로와 nginx가 찾는
경로가 갈려 파일이 보이지 않게 됩니다.

**스케줄러를 워커에 내장하지 않았다.** Celery는 `-B` 옵션으로 beat를 워커에 붙일 수
있지만 그렇게 하면 **워커를 2개로 늘리는 순간 배치가 두 번 실행됩니다.** 워커는 수평
확장의 대상이고 스케줄러는 단일 인스턴스여야 하므로, 같은 이미지를 쓰되 커맨드만 다른
별도 서비스로 분리했습니다.

**DB 이미지를 공식 `postgres:16`이 아니라 `pgvector/pgvector:pg16`으로 잡았다.** 벡터
검색에 `CREATE EXTENSION vector`가 필요한데 공식 이미지에는 확장이 없어 마이그레이션이
실패합니다. 데이터 디렉터리 형식은 호환되므로 볼륨은 그대로 유지됩니다.

**헬스체크에 `start_period`를 넉넉히 줬다.** 컨테이너 진입점이 기동 시 DB 마이그레이션을
실행하기 때문에, 첫 기동은 정상적으로도 수십 초가 걸립니다. 이 시간을 고려하지 않으면
정상 배포가 헬스체크 실패로 재시작 루프에 빠집니다.

### 이 구성의 한계

의도적으로 감수한 것들입니다.

- **단일 장애점** — 인스턴스가 죽으면 DB까지 함께 죽습니다.
- **배포 중 다운타임** — `up -d --build`가 컨테이너를 갈아끼우는 동안 요청이 끊깁니다.
- **수평 확장 불가** — 트래픽이 늘어도 인스턴스를 키우는 것 외에 방법이 없습니다.
- **백업이 볼륨 스냅샷 의존** — 시점 복구가 안 됩니다.

검증 단계에서는 이 네 가지 모두 실제 위험이 아니었습니다. 문제가 되는 시점이 오기 전에
옮기는 것이 계획이었습니다.

## 목표 구성

트래픽과 팀 규모가 늘어날 때를 상정한 구성입니다.

```
                        Internet
                           │
                   ┌───────▼────────┐
                   │  Route 53 DNS  │
                   └───────┬────────┘
                           │
                   ┌───────▼────────┐
                   │  ALB  (:443)   │  ← ACM 인증서
                   └───────┬────────┘
                           │
        ╔══════════════════▼══════════════════╗
        ║          ECS  (Private Subnet)      ║
        ║                                     ║
        ║   ┌────────────┐   ┌────────────┐  ║
        ║   │ API Service│   │   Worker   │  ║
        ║   │  1~N tasks │   │  1~N tasks │  ║
        ║   └──────┬─────┘   └──────┬─────┘  ║
        ╚══════════╪════════════════╪════════╝
                   │                │
       ┌───────────┼────────────────┼───────────┐
       │           │                │           │
┌──────▼─────┐ ┌───▼──────────┐ ┌───▼─────┐ ┌──▼──────────┐
│    RDS     │ │  ElastiCache │ │   S3    │ │     ECR     │
│ PostgreSQL │ │    Redis     │ │(uploads)│ │  (이미지)    │
└────────────┘ └──────────────┘ └─────────┘ └─────────────┘

지원: CloudWatch(로그·알림) · Secrets Manager(환경변수)
```

### 네트워크 분리

```
VPC (10.0.0.0/16)
├── Public Subnet  (10.0.1.0/24, 10.0.2.0/24)
│   └── ALB, NAT Gateway
└── Private Subnet (10.0.10.0/24, 10.0.11.0/24)
    ├── ECS Tasks (API, Worker)
    ├── RDS
    └── ElastiCache
```

인터넷에서 직접 닿을 수 있는 것은 ALB뿐입니다. 애플리케이션과 데이터 계층은 전부 프라이빗
서브넷에 두고, 아웃바운드가 필요한 경우에만 NAT Gateway를 경유합니다. 서브넷을 두 AZ에
걸쳐 두는 것은 가용성 때문이기도 하지만, ALB와 RDS Multi-AZ가 **애초에 2개 이상의 AZ를
요구하기 때문**이기도 합니다.

### Security Group — 소스를 CIDR이 아니라 SG로 지정한다

| SG | 인바운드 | 소스 |
|---|---|---|
| ALB SG | 443 | `0.0.0.0/0` |
| API SG | 8000 | **ALB SG** |
| RDS SG | 5432 | **API SG**, **Worker SG** |
| Redis SG | 6379 | **API SG**, **Worker SG** |

소스에 IP 대역 대신 다른 보안 그룹을 지정하는 것이 핵심입니다. 이렇게 하면 태스크가
재배치되어 IP가 바뀌어도 규칙을 고칠 필요가 없고, "ALB를 거친 트래픽만 API에 닿는다"는
의도가 규칙 자체에 드러납니다. 서브넷 CIDR로 열어두면 같은 서브넷의 다른 리소스까지
암묵적으로 허용됩니다.

### 왜 바로 이 구성으로 시작하지 않았나

이 구성은 월 $179 규모이고([02. 비용 설계](02-cost.md)), 구성 요소가 늘어난 만큼 초기
설정과 디버깅에 시간이 듭니다. 검증 단계에서 필요한 것은 가용성이 아니라 **오늘 안에
동작하는 HTTPS 주소**였습니다.

대신 옮겨갈 때 걸림돌이 될 것들은 처음부터 피했습니다. 파일 저장을 인터페이스 뒤에 두어
로컬 디스크와 S3를 바꿔 끼울 수 있게 했고, 설정을 전부 환경변수로 빼두었으며, 컨테이너
이미지를 그대로 ECS 태스크에 쓸 수 있도록 빌드했습니다. 마이그레이션은 진입점에서
자동으로 실행되므로 어느 환경에서든 기동 절차가 같습니다.
